HOW IT BEHAVES
-------------------------------------------------------------------
  - Swiping is native scrolling with scroll-snap, not a JS drag, so
    it uses the phone's own physics and momentum and feels like the
    rest of the platform.
  - Arrows step one item at a time and grey out at each end, so it
    is clear where you are in the set.
  - A plain "1 / 3" sits between them.
  - The text under the photo is part of the slide, so it changes
    with the picture.
  - The track takes keyboard focus and answers to left/right arrow
    keys.
  - Reduced-motion preferences are respected.
  - Above 899px the script unbinds itself completely.

Page height at 375px: 9,262 -> 7,501. From where this started before
the mobile work, 10,247.


THREE THINGS THAT WENT WRONG ON THE WAY
-------------------------------------------------------------------
1. MY DESKTOP CHECK REPORTED 186 CHANGED ELEMENTS ON A DESKTOP THAT
   HAD NOT MOVED. It keyed each element by its position in document
   order, and inserting the wrappers shifted every index after them.
   It now keys on class name plus occurrence. This is the second
   time that test has needed fixing before it could be trusted; the
   self-comparison it prints beside the real one is what catches it.

2. THE ARROWS WERE LANDING 18px OFF and scroll-snap was quietly
   covering for it. The offset the code used is measured from the
   spread, not from the track, and the track carries a negative
   margin so the slides can bleed to the screen edge. Both the
   arrows and the counter now work from live measurements instead.

3. A MOUSE DRAG DOES NOT SCROLL A NATIVE OVERFLOW CONTAINER — that
   is touch behaviour. My first swipe test reported a dead carousel
   that was in fact working. Worth knowing before anyone concludes
   the same thing.
